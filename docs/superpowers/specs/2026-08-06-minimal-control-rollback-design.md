# 最小化控制协议回退设计

日期：2026-08-06

## 1. 目标

删除本轮 P0 改造新增的 `ask_user`、`request_confirmation`、`finish` 三个控制工具，以及只为这三个工具服务的细粒度授权状态，恢复项目原有的 JSON 动作协议。

本次采用定向回退，不整体撤销 P0 提交。与三个控制工具无关、已经证明有价值的修复继续保留。

## 2. 设计原则

### 唯一性原则

同一种职责只保留一套实现：

- 对话控制只使用原有 JSON 动作：`chat`、`ask_user`、`confirm`、`done`。
- 本地文件是否允许修改，只使用 `designConfirmed` 判断。
- 普通工具只从原有工具注册表注册；`use_skill` 继续作为已有的特殊工具处理。
- 文件修改前的版本保存，只保留原有 `saveCheckpoint` 机制。
- 工具执行结果只保留结构化 `ToolResult` 作为内部返回格式。

### 对抗性审查原则

不只验证正常流程，还主动验证模型输出错误、授权边界混乱、Windows 命令执行失败、重试内容串入最终回复等情况。

## 3. 删除内容

### 3.1 三个控制工具

删除 `src/orchestrator/controlTools.ts`，并删除 Agent 中对以下内容的注册和拦截：

- `ask_user`
- `request_confirmation`
- `finish`

模型不再通过工具调用控制一轮任务的结束、提问或确认。

### 3.2 与控制工具绑定的授权状态

删除只为新控制协议增加的状态和判断：

- `authorization`
- `authorizationCounter`
- `workspace_write`
- `remote_git`
- `destructive_revert`
- 根据授权范围动态增减工具的逻辑

这些状态与原有 `designConfirmed` 表达了重复含义，继续共存会让同一次写入出现两套判断依据。

### 3.3 新增的文件级 checkpoint

删除依赖 `authorizationId` 的新 checkpoint manager 及其专用测试。项目继续使用原有 `saveCheckpoint`，避免两套文件恢复机制并存。

### 3.4 控制工具专用提示词、Skill 说明和评测指标

删除要求模型必须调用三个控制工具的提示词和 Skill 说明。

删除只用于证明三个控制工具被正确调用的指标，例如 Native Control Action Rate、控制工具协议违规率和控制工具 fallback 率。原有任务成功率、工具调用准确性、越权写入、重试和验证类指标继续保留。

## 4. 恢复后的控制流程

模型最终输出原有 JSON 动作，程序解析后执行：

- `chat`：直接回答用户并结束当前任务。
- `ask_user`：信息不足时向用户提问，等待用户补充。
- `confirm`：方案明确但需要修改文件时，请用户确认。
- `done`：修改和验证完成后结束任务。

确认后只设置 `designConfirmed = true`。写工具真正执行前再次检查该值；未确认时，即使模型错误调用写工具，程序也必须拒绝。

当任务以 `chat` 或 `done` 结束时，清除本次任务的 `designConfirmed`，防止上一个任务获得的修改权限被下一个任务继续使用。

JSON 解析继续保留，并覆盖 Markdown 代码块、正文中包含花括号、多个 JSON 片段和格式错误等情况。格式错误只能被当作普通文本或解析失败处理，不能因此获得修改权限。

## 5. 保留的独立修复

以下内容与三个控制工具没有依赖关系，继续保留：

### 5.1 Windows 命令执行

在 Windows 上运行 `npm`、`pnpm`、`yarn` 等命令时，正确处理对应的 `.cmd` 启动文件，避免直接启动时报 `EINVAL`。

### 5.2 代码搜索

保留对 `.mjs`、`.cjs`、`.mts`、`.cts` 等文件的搜索支持，以及相对路径、文件名匹配和大文件保护。

### 5.3 模型请求重试

模型请求遇到 429 或 5xx 后重试时，丢弃失败请求已经产生的不完整文本和工具调用，避免它们混入最终回复或后续对话记录。

### 5.4 结构化工具结果

保留内部 `ToolResult`，使用 `ok`、`code`、`message`、`retryable` 表达工具是否成功、失败原因和是否值得重试。它不是新工具，也不增加任务状态。

### 5.5 真实验证和评测框架

保留能够真实运行测试、构建、lint 和 TypeScript 检查的验证逻辑，以及与三个控制工具无关的评测脚本和报告生成能力。

## 6. 本次不处理的内容

- 不新增 Sandbox 或 Docker。
- 不重写整个 Agent 循环。
- 不在本轮补齐 Anthropic provider 的工具调用能力。
- 不顺带重构 `/revert`、前端确认按钮或其他历史逻辑；这些问题只列入最终审查报告，避免回退任务无限扩张。
- 不修改用户现有的 `config/model.example.json` 删除状态。

## 7. 实施方法

使用定向代码修改完成回退，不执行 `git reset --hard`，也不整体 revert P0 提交。这样可以删除冗余控制协议，同时保留已经验证有效的独立修复。

实施完成后提供一张逐项审查表，列出 P0 中每一类修改的处理结果：保留、删除或暂不处理，并说明原因。

## 8. 验证方案

至少执行以下测试：

1. 未确认时调用写工具，必须被拒绝。
2. 用户确认后，允许执行本地文件修改。
3. `chat` 或 `done` 结束后，再次写入必须被拒绝。
4. 包含 Markdown、代码花括号和多个 JSON 片段的回复，仍能找到正确的最终动作。
5. 错误 JSON 不能让程序进入已确认状态。
6. Windows 上真实执行项目的 npm 测试命令。
7. 搜索 `.mjs` 文件并验证命中结果。
8. 模型请求重试后，最终回复不包含第一次失败请求的残缺内容。
9. 运行与改动范围相关的单元测试、构建、lint 和 TypeScript 检查。
10. 检查 Git 暂存区，确认没有包含 `config/model.example.json` 或其他用户修改。

## 9. 完成标准

- 工具列表中不存在三个新增控制工具。
- 代码中不存在新旧两套授权状态并行判断。
- 原有 JSON 动作协议可以完成回答、提问、确认和结束任务。
- 未确认写入与跨任务权限残留均被测试拦截。
- Windows、搜索、重试、结构化结果和验证修复仍然通过测试。
- 最终审查报告能明确说明保留和删除了什么，不使用模糊术语。
