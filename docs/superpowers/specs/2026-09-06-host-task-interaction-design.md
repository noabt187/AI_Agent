# AI Agent 宿主任务交互设计：保持 PageCraft 插件不变

日期：2026-09-06。

状态：已实施；宿主自动回归与真实浏览器夹具验收通过。实际生成、后台／双标签手工验收及插件既有问题的边界见 `docs/testing/2026-09-06-host-task-interaction.md`。

代码基线：`ebf139fa5d5b0eec3eac2c05de00df8e19cd4e42`（`lwm_dev`）。PageCraft 目录树基线：`7ae542f9c7fcf9bb8563b409c91a4c5f248134a7`。

## 1. 目标与约束

用户在 PageCraft 内发起 Agent 任务后，不必关闭插件或返回主聊天区，就能知道任务是否在运行、是否需要确认，并完成必要操作。

本次只修改 AI Agent 宿主：

- 不修改 `plugins/dsh-frontend-feedback` 中任何源码、Skill、清单、测试或构建包；不重建、不重装插件。
- 不修改 DeepSeek Harness 或当前 PPT 项目、预览服务器。
- 不改变插件调用 `session.prompt(content, 'queue')`、订阅或 `getSnapshot().running` 的语义。请求被接受不等于执行完成；等待确认不伪装为运行中。
- 不读取、替换或隐藏 PageCraft 内部 DOM 文案，不拦截其请求来伪造任务成功，不自动点击插件按钮。
- 保留现有 Cordis、单会话 FIFO、RunStore、TaskState、版本化确认和工具写权限检查；不新增数据库或另一套任务调度器。
- 不处理此前发现的插件初始化 `response.json is not a function` 问题；该问题需要修改共享插件，属于另一个范围。

明确边界：宿主提供权威状态和操作入口，但不能承诺未改动插件内部每一句进度文案都会同步。插件不再运行时仍显示“正在规划”的情况，由宿主可见提示说明真实运行状态；不得据此声称已经修正插件内部状态。

## 2. 已验证的原因

- `web/src/App.tsx` 已持有待确认方案及确认、修订、撤销操作，但确认区属于主聊天布局。
- PageCraft 把自己的界面 portal 到 `document.body`，现有覆盖层使用 `zIndex: 10000`，主聊天确认区可能被遮住。
- `web/src/plugins/sessions.ts` 只向旧插件提供是否运行，增加新字段也不会使旧插件自动消费这些字段。
- 实测 `session-012` 中主会话已结束，回复要求确认；宿主 Task 却为 `active`、`pendingConfirmation` 为空，文档 Job 为 `source_ready`，插件仍显示“正在阅读文档并规划目录”。因此不只是层级遮挡，还存在非结构化结果没有可执行确认记录的情形。
- 运行事件已有 `result`、`task` 和 `run`；`AgentResult.chat` 已能标记 `protocolFallback`，但 RunRecord 未持久化该诊断，刷新后难以区分正常聊天和协议回退。

这次设计延续既有 `2026-09-06-agent-pagecraft-state-boundaries-design.md` 中任务归属和退出隔离规则，不重做其状态机。

## 3. 方案选择

选择：宿主统一任务状态卡 + 顶层交互面板 + 持久化结果诊断。

比较过的替代方案：

- 仅提高原确认区层级：改动少，但无法处理没有正式确认记录、失败、断线恢复及插件持续显示忙碌的问题。
- 等待确认时自动关闭 PageCraft：会打断编辑、焦点和未保存草稿，也依赖插件关闭能力，不采用。

宿主统一方案不依赖 PageCraft 私有实现；以后同样通过宿主提交请求的插件可以复用。当前来源只可靠区分“聊天”和“插件”，不猜测具体插件名称。

## 4. 用户体验

### 4.1 常驻任务状态卡

在宿主根部渲染一个紧凑的任务状态卡，展示当前会话和真实状态。存在运行、待处理交互或尚未查看的终态时可见；关闭 PageCraft 不销毁它。

- 宿主使用独立 portal，层级高于当前 PageCraft 普通覆盖层，位置避开右上角插件关闭按钮，移动端限制宽度。
- 只覆盖卡片自身区域，不能用透明全屏容器挡住插件操作。
- 展示来源“插件任务／Agent 任务”、简短状态和“查看详情”；运行时可展开停止操作。
- 需要处理的状态不定时消失。可收起详情，状态卡仍保留；已查看的普通终态可以关闭。
- 卡片讲述的是 Agent 执行状态，不把 Run 完成描述为“PPT 已生成”或“图片已同步”。

### 4.2 顶层交互面板

正式确认或补充问题首次到达当前会话时，自动展示宿主交互面板。用户可以在 PageCraft 上方阅读方案、选择候选项、确认、修改或回复。

采用宿主根文档中的原生 `<dialog>` 和 `showModal()`，并沿用灰白主题；不放进 PageCraft iframe。原生模态对话框进入浏览器顶层，能覆盖当前插件的普通 portal，背景暂时不可交互，但组件保持挂载。依据：[MDN showModal](https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement/showModal)。

- 初始焦点放到标题或方案内容，不默认放在“确认执行”上，避免误按回车授权。
- 提供“收起”按钮：只关闭宿主面板，保留待处理状态，不撤销方案、不停止运行。
- 正式确认提供“确认执行／继续分析”（依据写权限类型）、“调整方案”和“撤销本次确认”。保留候选方案选择、比较和写权限警示。
- 处理成功且服务端状态已更新后收起，插件页面、滚动和未保存编辑保持原样。
- 无正式确认记录时不出现可授权的“确认执行”按钮。
- 不自动切换会话；后台会话事件不能抢占当前面板。切回该会话后，从权威快照展示其待处理状态。

### 4.3 异常和普通回复

当运行终止且 Task 仍为 active：

- 合法 `chat`：显示“本轮已结束”，允许查看回复和补充说明，不认定任务完成。
- 已知协议回退：显示“Agent 已回复，但未返回有效任务指令”，展示回复并提供“请求重新给出方案”。
- 旧记录缺少结果类型：显示“本轮已结束，请查看回复”，不反向猜测是否为协议错误。

“请求重新给出方案”仅在用户明确点击后提交一次宿主请求，要求根据当前任务和上一轮回复整理可确认方案，本轮不执行修改。此请求本身不授予写权限、不自动确认、不自动重试；后续只有正式方案经过用户确认才可写入。

## 5. 状态来源与一致性

### 5.1 不再维护第二个执行状态机

新增纯函数 `deriveTaskInteraction`，由已验证的 SessionRuntime 视图、TaskState 和 RunRecord 派生展示状态；展示状态不写回 TaskState，也不反向控制插件 Job。

| 服务端及连接依据 | 宿主显示 | 允许的主要操作 |
| --- | --- | --- |
| 请求尚未获得服务端接受 | 正在提交 | 查看；不得宣称正在执行 |
| Run queued | 已排队 | 查看排队状态 |
| Run running | 正在执行 | 查看过程、停止此运行 |
| 正在停止尚未收尾 | 正在停止 | 查看，禁用重复停止 |
| 当前 Task awaiting_confirmation 且有匹配记录 | 等待确认 | 阅读、选择、确认、修订、撤销 |
| 当前 Task awaiting_input | 等待补充信息 | 阅读问题、提交回答 |
| 当前关联 Run failed / interrupted | 执行失败／运行中断 | 查看错误、符合原规则时继续 |
| 当前关联 Run cancelled / Task paused | 已停止／已暂停 | 查看；符合原规则时继续 |
| Run completed + Task active | 本轮已结束 | 查看回复、补充说明 |
| 同上且 protocolFallback | 需要处理回复 | 查看、请求重新给出方案 |
| 当前 Task completed 且本轮无更晚失败／取消 | 任务已完成 | 查看结果；不承诺产物验收通过 |
| 当前 Task cancelled | 任务已取消 | 查看历史 |
| 流断开、快照未核实或归属矛盾 | 正在核实状态／连接中断 | 重新连接、查看已有记录；暂禁授权操作 |

派生规则：

1. 按 `sessionId + taskId + taskRevision + runId` 校验归属；不能取数组最后一条记录就当成当前执行。
2. 当前运行优先展示，队列数量另列；排队请求不能提前覆盖正在执行的任务状态。待确认面板可先显示，但在前一运行完成收尾、快照确认可操作之前禁用提交。
3. 结果事件先于任务最终快照到达时，不提前宣布完成或开放确认。取消、失败和过期版本不能被较早的 done/result 覆盖。
4. 传输 EOF、插件不再 running、接口返回 200 都不是 Task 完成证据。复用现有恢复轮询和快照序号保护。
5. 无运行且 Task 终态尚未核实，不无限显示“正在生成”；明确标为状态核实或本轮结束。

### 5.2 增量记录，不迁移整库

RunRecord 增加可选展示元数据：

- `origin: 'composer' | 'plugin'`：由现有 App 提交入口传递，通过宿主 HTTP 请求的可选字段落盘；只用于展示，不参与授权。CLI 和旧记录缺省显示“Agent 任务”。
- `resultMeta: { action: 'chat' | 'ask_user' | 'confirm' | 'done'; protocolFallback?: true }`：由服务端实际收到的 AgentResult 生成，不能从客户端请求或回复关键词取得。

元数据在运行终态落盘之前，通过已有串行 RunStore 写入；不改变终态不可覆写规则。回复内容复用本轮 `messageIds` 关联的 assistant 消息，不另存一份可能不一致的全文。

旧 runs.json 缺少字段仍可读取；不批量改写旧会话，不新增 TaskState schema 版本。当前旧会话的 active + terminal 组合也必须显示本轮结束，不能因缺少新元数据而继续显示运行。

宿主继续接受不携带 origin 的旧请求。插件依旧使用原 prompt 服务，不新增必需注入服务或字段。

## 6. 操作与授权

### 6.1 正式确认

复用现有确认、修订、方案选择及 `pending-confirm` 撤销接口。主聊天区和顶层面板共用一个 `TaskInteractionActions` 控制器和确认内容组件，不能各自保存一份待确认方案。

- 按钮捕获它展示的 `sessionId/taskId/taskRevision/confirmationId`，不在点击后悄悄改为最新方案。
- 服务端继续在入队和实际执行前验证版本及工作目录；重复确认、过期确认、非法候选项拒绝执行。
- 提交中锁定同一交互键。409 保留上下文并重新读取，提示“方案已变化，请重新查看”；不自动确认新版本。
- 非确定网络失败时先核实记录，不自动重发可能已被接受的确认。
- “撤销本次确认”沿用清除待确认并暂停任务的语义；“收起”不调用该接口。

### 6.2 补充回答和重新整理方案

这些操作不是确认，也不是允许恢复旧写权限的 resume。为宿主自己的可选 TaskInputControl 增加 `followup`：绑定 `taskId/taskRevision/sourceRunId`，不带 confirmationId。

- 仅用于 awaiting_input，或当前运行已终止、Task active 的后续说明；必须没有其他正在执行的同会话运行。
- 在接收及出队时校验任务版本、上一运行归属和目录快照；失败返回冲突，不把回答送给另一个任务。
- 作为同一任务的一次修订，递增 revision，保留原目标、问题和回复为背景，以最新说明为当前请求，清除旧确认、approvedProposal 和写授权。
- 原有插件 prompt 和聊天输入行为不变；新增控制只由宿主面板使用，但安全性由服务端校验保证。
- 旧记录若缺少可核实的 task/run 归属，只提供查看和返回主会话发起新请求，不伪造 followup 标识。HTTP 入队校验与出队校验均不能把来源字段当作可信授权。
- 回复草稿按交互键隔离；切换任务不得把草稿自动发给新任务。方案文字仅作为数据展示，不作为宿主控制指令执行。

### 6.3 停止

复用停止路径，并为宿主停止请求增加可选 `expectedRunId`：服务端在队列当前运行上核对后再中断。旧请求不带该字段的兼容语义不变，新的宿主控制必须携带它。

如果用户看到的 A 已结束、B 已接替，停止 A 必须返回状态已变化，不能停止 B。停止不清空排队任务、不回滚文件、不关闭插件。队列仅含 queued 时不展示会误伤其他运行的停止按钮。

## 7. 面板生命周期、焦点和恢复

- 正式确认交互键为会话、任务、版本、confirmationId；补充或异常交互键为会话、任务、版本、sourceRunId、交互种类。
- 当前页面内每个需处理交互最多自动展开一次。收起后保持状态卡，轮询和重渲染不反复抢焦点；刷新后从服务端恢复未处理状态。
- 自动展开只在页面可见且当前会话匹配时发生；页面隐藏期间记录未处理状态，重新可见后核实快照再展示。
- 运行中的任务卡不自动弹出模态框。已知协议异常弹出一次说明；正常 chat 不自动弹框。
- 面板与插件均保持独立挂载。方案变化或切换会话时失效旧操作；不卸载 PageCraft 来控制其开关。
- 宿主面板打开时，局部捕获并消费 Escape，避免冒泡到 PageCraft 的 window 监听器；输入法组合期间的 Escape 不视为关闭请求。
- 原生 dialog 的 cancel 事件只走“收起”路径，不调用 abort 或撤销确认；事件可取消，需显式管理默认关闭行为。依据：[MDN cancel event](https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement/cancel_event)。
- 关闭面板恢复此前仍有效的焦点；此前节点已消失时回到宿主状态卡。背景插件不能接收到确认面板的回车／Escape 并执行自身动作。
- 断线时保留最后已知内容并标记过期，禁用授权操作。复用 SessionRuntime 的恢复节流、revision/sequence 和旧回调丢弃机制。
- 本轮不新增后台全会话轮询、全局快捷键框架或跨窗口协调服务。多标签同时操作的正确性由服务端版本校验保证。

## 8. 文件职责与实施分层

拟新增的宿主内部单元：

- `web/src/taskInteraction.ts`：归属选择、展示状态、可用操作的纯函数。
- `web/src/TaskInteractionHost.tsx`：状态卡、顶层面板、焦点及自动展开生命周期。
- `web/src/TaskInteractionContent.tsx`：复用现有确认表单，展示问题、回复及异常；不持有执行权威状态。
- `web/src/useTaskInteractionActions.ts`：共用确认、撤销、跟进、继续和停止的提交与失效处理。

需要调整的现有宿主文件：

| 范围 | 文件 | 内容 |
| --- | --- | --- |
| 运行结果与恢复 | `src/state/runStore.ts`、`src/server/sessionApi.ts` | 可选来源和结果诊断；正确持久化时序 |
| 请求入口、队列 | `src/server/coreRoutes.ts`、`src/server/promptQueue.ts` | 可选来源、版本化停止；保留现有排队行为 |
| 任务控制 | `src/orchestrator/types.ts`、`taskInput.ts`、`taskState.ts` | 无写授权的版本化 followup；必要的旧状态校验 |
| 宿主前端接线 | `web/src/App.tsx`、`api.ts`、`sessionRuntime.ts`、`styles.css` | 保留来源、权威状态接入、复用确认逻辑、宿主面板样式 |

按“数据与归属 → 控制保护 → 宿主 UI → 同包验收”顺序实施，每步有独立测试。无需更改 `web/src/plugins/sessions.ts` 对旧插件的公开行为；也不需要通过修改插件的运行标志欺骗其刷新逻辑。

## 9. 验收标准

### 自动测试

1. 运行正常结束、正式确认、补充问题、协议回退、失败、中断、暂停、完成分别派生正确展示；未知旧记录不推断授权或产物成功。
2. 多运行排队、跨会话、旧快照回流、终态与 task 事件交错不显示另一任务的控制按钮；断线不伪装为成功。
3. resultMeta/origin 经现有 runs.json 保存和重读后保留，旧记录兼容，终态不可覆写。
4. 主界面和宿主面板共用同一确认身份；重复点击、多标签旧确认、修改方案、换目录、延迟出队均不得授权错误任务。
5. followup 绑定旧版本时拒绝；有效回答及重新整理请求均清除旧写授权；没有正式确认记录时不能点确认执行。
6. expectedRunId 过期时不能中断后继运行；收起和 Escape 不调用停止或撤销接口。
7. 挂载真实宿主 UI 与未修改的 PageCraft bundle，打开插件，再注入可控的宿主确认和异常事件；不得只用启动按钮的 SSR 测试代替交互测试。
8. dialog 模态层级、焦点、Escape 穿透需要真实浏览器验收，不能因 jsdom 测试通过而宣称通过。

### 浏览器验收

- 在 PageCraft 文档或文件工作区保持打开时触发正式确认：宿主面板立即可见、可阅读可操作，不必退出插件。
- 收起、确认、修订、撤销分别检查；确认后插件继续读取原任务生成结果，未保存草稿和编辑视图保留。
- 重现“回复要求确认但实际无 pendingConfirmation”：宿主显示本轮已结束／需要处理回复，不伪造确认按钮，不自动发消息；用户能在宿主面板查看并请求整理方案。
- 对源文件尚未生成的暂停任务，宿主不能宣称正在生成；即使插件内部旧文案未变，真实状态卡也持续可见。
- 覆盖关闭宿主面板、关闭 PageCraft、停止 Agent 三种独立操作；运行记录和插件开关不能相互串联。
- 在窄屏、后台回到前台、刷新、断线恢复、切换会话和两个标签的旧确认场景下复核。

### 交付检查
