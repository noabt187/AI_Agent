# 项目首页截图

[返回项目首页](../../README.md)

首页使用本目录中的 4 张真实界面截图。更新截图时，保持下列文件名不变即可替换对应图片，不必重新修改首页链接。

## 拍什么、保存成什么

| 文件名 | 要拍的界面 | 一张图里需要看清的内容 |
| --- | --- | --- |
| `01-workbench.png` | AI Agent 主工作台 | 灰白水墨界面、已选择的项目、清晰的开发需求，以及一段简洁的方案或执行结果；保留会话与任务状态 |
| `02-dom-feedback.png` | PageCraft 页面评注 | 一个真实页面、一个高亮选中的 DOM 元素、具体的修改意见，以及已有 2–3 条意见的评注队列 |
| `03-presentation.png` | PageCraft 演示文稿 | 一套已经生成的文稿、页面导航，以及有标题、图文或图表的完成页；不要停在空白封面或生成等待界面 |
| `04-source-workspace.png` | PageCraft 文件工作区 | 同屏显示真实文件树、可读的源码和页面预览；尽量选能对应到右侧页面内容的源码，保留保存状态 |

统一存放在**仓库根目录下的 `docs/screenshots/`**：

```text
AI_Agent/
├── README.md
└── docs/
    └── screenshots/
        ├── README.md                 ← 这份说明
        ├── 01-workbench.png
        ├── 02-dom-feedback.png
        ├── 03-presentation.png
        └── 04-source-workspace.png
```

图片请真正保存为 PNG，不要只把 JPG 的扩展名改成 `.png`。保持文件名完全一致，避免出现“截图(1).png”这样的默认命名。

## 建议的演示内容

最好使用同一个无敏感信息的演示项目，让读者能连贯理解“提出需求 → 指出修改位置 → 查看成果”。示例数据可以用于演示，但不要把它包装成真实客户数据或实际生产指标。

### 图 1：一眼看懂这是开发工作台

选择一个干净的演示会话，提出类似「分析项目首页，给出布局优化方案，先不要修改文件」的请求。等回复稳定后拍摄，避免密集报错、很长的测试日志或大量无关历史。

### 图 2：最重要的 DOM 能力

在 PageCraft 打开目标项目地址，开启“选择元素”，选中卡片或标题；输入「标题层级加大，减少上下留白」等具体要求。队列中可再准备一条「新增趋势图，与上方卡片对齐」。保留选区高亮与评注面板。

只为截图准备时，意见留在队列即可，不必点击“发送给 Agent”。如果还要展示区域框选，可再补一张独立截图，不必挤进同一张图。

### 图 3：展示已经做出来的文稿

选择最完整、美观的一页，优先使用图文混排或有图表的内容页。左侧保留其他页面的导航，让人看出这是多页文稿。可以展示自备图片已经放入页面的效果；不要展示加载中、生成失败或空图片槽位。

### 图 4：证明结果可以继续编辑

在“文件”里打开页面源码或 `deck.json`，定位到右侧预览中的同一段标题或内容。调整分栏宽度，让源码和预览都能读清。没有必要为了拍图修改或保存代码。

## 画面规格与隐私

- 横向截图，建议宽度至少 1600 像素；尽量统一窗口宽度、主题和缩放，文字不能小到无法阅读。
- 只截项目应用内容，避开桌面、聊天软件、开发者工具和系统通知；无需把 Codex 外框一起截进去。
- 尽量保留完整功能关系，不要只截孤立按钮；清理遮挡内容的菜单、气泡和无关弹窗。
- 不出现 API Key、令牌、邮箱、私人对话、敏感文件内容或内部服务器地址。个人用户名路径也尽量避开。
- 建议单张控制在 2 MB 左右，以文字清晰为先；可先给原图，后续再统一无损压缩。

```markdown
![AI Agent 工作台：项目会话、开发方案与任务状态](docs/screenshots/01-workbench.png)
```

替换截图后请一并提交图片文件，并核对对应的图片说明仍然准确。不要把 Markdown 图片语句放进 HTML 注释，否则 GitHub 不会显示图片。

截图前建议收起无关的任务状态卡，避免“未返回有效任务指令”等提示遮挡画面。DOM 评注图最好包含已填写的修改意见和非空队列，以便读者理解选中元素之后如何交给 Agent。
